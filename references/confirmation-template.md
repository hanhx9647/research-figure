# Confirmation stage

确认优先（confirmation-first）是本 skill 的核心特色。收到论文、摘要、方法描述或研究笔记时，
**先输出下面的确认草稿，不要直接生成图。**

## 输出模板（固定七段）

生成前必须以纯文本输出以下内容，段标题不得改动：

```text
一、我理解的研究目标
二、流程阶段
三、输入与输出
四、模块之间的关系
五、反馈回路
六、目前存在的歧义
七、需要你确认的内容
```

各段要求：

1. **我理解的研究目标** —— 一句话说清这张图要回答什么问题、给谁看。
2. **流程阶段** —— 按阅读方向列出主干阶段，每个阶段一句话，标明编号。
3. **输入与输出** —— 分别列出整图的输入端与最终产出；中间产物写在阶段里。
4. **模块之间的关系** —— 逐条列出「A → B（关系说明）」，箭头方向必须明确。
5. **反馈回路** —— 列出所有回环与迭代；没有就写「无」。
6. **目前存在的歧义** —— 原文没说清、或存在多种读法的地方，逐条列出，**不要自行补全**。
7. **需要你确认的内容** —— 编号列出待确认项，用户可只回答其中某几条。

第 6、7 段是重点：宁可多问，不要臆造科学关系。对于科研图，一条编造的因果链比一张丑图危害大得多。

## approved 门禁（硬性规定）

状态写在 `output/figure_contract.yaml`：

```yaml
approved: false
```

**`approved: false` 时：**

- 不得生成最终 PPTX
- 不得输出最终图片（PNG / PDF）
- 不得写入 `output/` 下的成品文件
- 只允许生成：确认草稿、`figure_contract.yaml` 本身、编辑性报告草稿

**置为 `approved: true` 的条件：**

- 用户已确认研究目标与主要阶段；或
- 用户明确答复了第 7 段中全部阻断性问题；或
- 用户说「按你的理解生成」之类的明确授权（需在决策日志中记录原话）

## 决策日志

每次用户修订，追加一条记录，避免改一项就要重来：

```yaml
decision_log:
  - at: 2026-10-08T15:30:00
    item: stages
    from: ["数据清洗", "特征工程", "建模"]
    to: ["数据清洗", "特征选择", "建模"]
    by: user
```

## 局部修订

用户只改某一项时，只更新对应字段，其余保持不变，并在决策日志里记一笔。
不要因为一次小修改就重新走一遍完整确认流程。
